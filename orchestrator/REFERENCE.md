## Fast mode

If you ever want fast mode: it needs **both** `-c service_tier=fast` **and** `--enable fast_mode`, is ChatGPT-auth only, and burns credits at 2.5× the standard rate (measured on the prior generation). On the API side, Fast mode replaced Priority Processing on 2026-07-30: sol only, 2× price for up to 2.5× speed, same intelligence — irrelevant for background workers, whose latency the orchestrator absorbs.

## Profiles vs pinned flags

The dispatch template pins flags explicitly so the skill is self-contained regardless of `~/.codex/config.toml`. Profiles — `-p <name>` layering `~/.codex/<name>.config.toml` — can replace the pins, but codex hard-errors if legacy `[profiles.*]` tables remain in `config.toml`; explicit flags are more portable.

## Reaching gpt-5.6 from inside Workflow scripts

Workflow scripts' `model:`/`agentType:` params only take Claude values. Reach gpt-5.6 by wrapping: spawn a cheap Claude agent (`model: 'sonnet'`, `effort: 'low'`) instructed to compose the self-contained spec, run `codex exec` per `SKILL.md`, verify, and return the last-message file's content verbatim.

## Native Codex multi-agent (v2 stable as of 0.145.0)

Codex can spawn its own sub-agent threads; settings are unified under `[agents]` in config.toml (verified against 0.145.0 source: `enabled` default true, with an enabled `features.multi_agent_v2` taking precedence; `max_concurrent_threads_per_session`, alias `max_threads`; `default_subagent_model` / `default_subagent_reasoning_effort` for spawns that don't pick their own; per-role `[agents.<role>]` tables; `max_depth` is V1-only, ignored by V2). This skill deliberately doesn't orchestrate through it — you are the orchestrator, and separate dispatches keep per-worker kill/steer control. That's not just preference: V2 subagents live behind parent-owned mailboxes (path addresses like `/root/agent_a`, structured envelopes), and the app-server *rejects* external input to a spawned child (openai/codex#27173) — an outside orchestrator physically cannot steer inside a worker's fan-out. A worker may still fan out internally on its own; that's fine, your verification is on the final diff either way. (0.146.0 adjacent: agent-plugin manifests + marketplaces landed, including a Claude Code-format marketplace — cross-harness skill reuse exists, but changes nothing about dispatch mechanics.) The `spawn_agents_on_csv` batch primitive was **removed** in 0.145.0 (#34413; `job_max_runtime_seconds` survives only as a config no-op) — official docs still describe it, ignore them. As of 2026-08-13 the official subagent docs match the `[agents]` keys above and ship three built-in roles (`default`, `worker`, `explorer`); MAv2 delegation policy is `none` / `explicitRequestOnly` (new-thread default) / `proactive`, with the `ultra` reasoning level as the documented trigger for proactive delegation (see SKILL.md Notes). "Leaf model" work (#36892) points at per-subagent model assignment — Codex growing its own heterogeneous fleet; the per-worker-steering objection stands, but re-evaluate on next audit.

## Subagent role frontmatter (`.claude/agents/*.md`)

Beyond `tools`/`model`/`effort`: `disallowedTools` (denylist, applied before `tools`; both accept `mcp__<server>` patterns), `permissionMode`, `maxTurns`, `skills` (preload full skill content at startup), `mcpServers` (scope an MCP server to the worker so its tool schemas never touch main context — inline defs connect only for the worker's lifetime), `memory: user|project|local` (persistent cross-session agent memory), `hooks` (e.g. a `PreToolUse` validator as a hard constraint where prose briefs are soft), `background`, `isolation: worktree`.

## Cross-session messaging fine print

Same-machine delivery rides a per-session unix socket (`/status` → `Peer address`); each session exports `CLAUDE_CODE_MESSAGING_SOCKET`/`_TOKEN` to hooks and Bash, so a script can post into its own session — a push upgrade over polling progress files (first auth line: `{"type":"auth","token":...}`). Cross-machine and cloud routes go through Anthropic servers via Remote Control; containers can't reach host sessions. `dialogExpiry: "never"` keeps default-held messages until session end. Agent-team teammates are a separate roster, never listed by `ListAgents`; structured team protocol messages stay within the team.

## Agent teams mechanics

(`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS`): peer Claude sessions with a shared dependency-tracked task list, inter-agent messaging, plan-approval gates, and quality hooks (`TeammateIdle`, `TaskCreated`, `TaskCompleted` — exit 2 sends feedback and keeps the teammate working). Enabled in user settings 2026-08-02 (`env` block; sessions started after that). Mechanics (verified against docs + changelog 2026-08-02): since v2.1.178 every session is one implicit team — spawn teammates via the Agent tool's `name` param and message by name (`team_name` accepted but ignored; `TeamCreate`/`TeamDelete` removed — third-party guides describing them are stale). Subagent definitions double as teammate roles (`tools`/`model` honored; `skills`/`mcpServers` frontmatter ignored). Since v2.1.234 teammates inherit the lead's model unless the spawn names one or `CLAUDE_CODE_SUBAGENT_MODEL` is set (the "Default teammate model" `/config` setting was removed); they also inherit its effort level. **Naming trap:** while teams are enabled, any Agent spawn with a `name` launches as a teammate — even self-named by Claude during ordinary delegation — and a teammate's completion is an idle notification *without output*, so result-waiting flows stall; set the env var to `0` (hot-applied) to get named subagents back. Display default is `in-process` since v2.1.179 (**not** `auto`); split panes require tmux or iTerm2+`it2` and don't work in VS Code's terminal/Windows Terminal/Ghostty. Cost control: official estimate ~7× a standard session with plan-mode teammates — use Sonnet teammates, 3-5 of them, ~5-6 tasks each, shut them down when done. Known limits — no `/resume`/`/rewind` of in-process teammates (lead may message dead teammates after resume), no nested teams, no background subagents from an in-process teammate, task-status can lag (nudge or update manually), one fixed lead/team per session, and no automatic worktree isolation — partition by file ownership; teams are debating peers, not a locking system (task-claim locks don't guard file edits). State on disk (verified against docs 2026-08-13): mailboxes `~/.claude/teams/{team}/inboxes/{agent}.json`, roster `~/.claude/teams/{team}/config.json` (a teammate can read it to discover peers — brief them to, rather than hardcoding names), task list `~/.claude/tasks/{team}/`. The task list persists locally and survives resume; in-process teammates don't — tasks outlive their workers. Teammates never appear in `ListAgents`: the team roster and cross-session messaging are separate namespaces sharing one `SendMessage` tool, and structured team protocol messages stay within the team (cross-session is plain text only). Org kill switch: managed settings denying `SendMessage`/`ListAgents` also remove subagent and teammate messaging — a skill leaning on SendMessage-resume can be silently disarmed in a managed org.

No docker here, so container-per-worker isolation is out; per-worker ports/temp/DB names (Worker pools in `SKILL.md`) remain the tool.
